# Open Agent Governance Specification

**Version 0.1 — draft.** Entity model and authority grammar.

---

## Status of this document

This is a **descriptive** specification. Everything in it is implemented and
running; nothing here is planned. Where a thing is not built, this document says
so rather than specifying it — see [Out of scope for v0.1](#out-of-scope-for-v01).

That constraint is deliberate. A specification describing a roadmap is a press
release, and the first reader to check one against a running system decides which
kind they are holding.

The key words **MUST**, **MUST NOT**, **SHOULD** and **MAY** are to be
interpreted as described in RFC 2119.

---

## 1. Problem

An autonomous agent takes consequential actions. Existing governance answers
address the *model*: what it was trained on, how it scores on evaluations,
whether its outputs are toxic. None of that constrains what the agent is
permitted to **do** on a Tuesday afternoon with a payment API in reach.

The gap is not observability. Agent frameworks already emit traces. The gap is
**authority**: a statement, made in advance by an accountable human, of what a
specific agent may do, up to what value, until when, and under what conditions —
enforced before the action, and recorded whether it was allowed or refused.

This specification defines the vocabulary for that statement.

## 2. Entity model

### 2.1 Agent

A named autonomous system under governance.

An agent MUST have a **stable slug** and an **environment**. The pair is the
identity: the same slug in `dev` and in `prod` is **two agents**, with separate
authority. Implementations MUST NOT treat environment as a label on one agent,
because a credential issued for a test rung would otherwise reach a live one.

An agent MUST carry an **accountable owner** — a named human — before it can
hold any authority. An implementation MUST refuse to issue authority to an
unowned agent. This is the point at which governance becomes real rather than
descriptive: an agent nobody is answerable for cannot be given power.

An agent MAY be **discovered**: implementations SHOULD record an agent the first
time it speaks, holding nothing. You cannot govern what you cannot see, and
requiring registration before observation guarantees a population of ungoverned
agents.

### 2.2 Grant

A bounded authority, signed for by a named human.

A grant MUST name:

| Field | Meaning |
|---|---|
| `agent_id` | Who holds it |
| `principal_type`, `principal_id` | Who signed for it |
| `scope` | What actions it covers |
| `not_before`, `not_after` | The window it is valid in |
| `enforcement_mode` | Whether refusals are acted on — see §3.4 |
| `status` | `active`, `revoked`, `pending_approval`, `expired` |

A grant MAY additionally carry:

| Field | Meaning |
|---|---|
| `budget_amount_minor`, `budget_currency` | A spend ceiling |
| `budget_count` | A call ceiling |
| `conditions` | Predicates that must hold per action |
| `policy` | A rule expression evaluated per action |
| `parent_grant_id`, `depth` | Its position in a delegation tree |

A grant is **not** a role, a permission, or an API key. Those say who someone
is. A grant says what one named agent may do, bounded and expiring.

### 2.3 Trajectory

One governed episode: an agent pursuing one goal, with the steps it took.

A trajectory MUST carry a **stream key** and a **strictly increasing sequence
number** within that stream. A gap is therefore detectable, which is the
property most systems assert and few can demonstrate.

A trajectory MUST record its **steps in order**, each with a kind, and MUST
record the **taint state** entering and leaving each step (§2.5).

### 2.4 Decision

A request to act, and what was decided — recorded **before the agent is told**.

A decision MUST record its outcome as exactly one of:

| Outcome | Meaning |
|---|---|
| `allow` | Permitted |
| `deny` | Refused — no authority, or refused by policy or scope |
| `exhausted` | Refused — a budget ceiling was reached |
| `gated` | Refused — the context was tainted where a clean one was required |
| `review_sync` | Held, awaiting a person, blocking |
| `review_async` | Recorded, proceeding, flagged for later review |

A refusal MUST be recorded with the same fidelity as an allow. An implementation
that records only successful actions produces an audit trail in which controls
appear never to have fired, which is indistinguishable from having no controls.

### 2.5 Taint

Whether the context an agent acted on was trustworthy.

A taint label MUST record its `source_kind`, a `source_ref`, and the step
ordinal at which it entered. Implementations MUST propagate taint forward
through a trajectory: a step consuming tainted context produces tainted output.

### 2.6 Evidence batch

A set of sealed records, hashed into a Merkle tree, with a signed root.

A batch MUST record the **key that signed it** and the **custody of that key at
the time of signing** (§4). Reading custody from current configuration when a
proof is requested is non-conformant: a deployment that later moves to a
hardware key MUST NOT stamp that custody onto roots it signed years earlier
from an environment variable.

## 3. Authority grammar

### 3.1 The decision procedure

An implementation MUST evaluate a request against the following gates, **in this
order**:

| # | Gate | Question |
|---|---|---|
| 1 | `authority` | Is there any authority for this? |
| 2 | `status` | Is the grant active? |
| 3 | `window` | Is now inside the grant's window? |
| 4 | `scope` | Does the grant cover this action? |
| 5 | `clean_context` | Was the context clean, where that is required? |
| 6 | `bounds` | Do the per-action limits hold? |
| 7 | `policy` | Does the policy on the grant permit it? |
| 8 | `budget` | Is there room under the ceiling? |
| 9 | `review` | Does this need a person? |

The order is normative. Cheap structural checks precede expensive evaluation,
and **budget is debited last** — an action refused by policy MUST NOT consume
budget.

### 3.2 Trace states

An implementation SHOULD be able to render, for any decision, what each gate
did. Each gate MUST be reported as exactly one of:

| State | Meaning |
|---|---|
| `passed` | The gate was evaluated and permitted |
| `refused` | The gate was evaluated and refused |
| `not_reached` | An earlier gate refused first |
| `not_applicable` | The grant carries nothing for this gate to check |

`not_applicable` MUST NOT be collapsed into `passed`. "This grant carries no
policy" and "the policy permitted it" are different facts, and a grant with no
rule at all MUST NOT display as though a rule had approved the action.

A trace MUST be derived from the same evaluation that produced the decision. A
second walker over the same rules will drift, and a trace that disagrees with
its decision is worse than no trace: it is a confident account of something that
did not happen.

### 3.3 Delegation and attenuation

A grant MAY delegate to a child grant. A child **MUST NOT exceed its parent on
any axis**: scope, window, budget, conditions, or enforcement mode.

Attenuation MUST be enforced at issue time, by construction, rather than checked
at use time. A tree of valid grants therefore cannot sum to more authority than
its root.

A debit against a child grant MUST debit **every ancestor**. The parent's
ceiling is the real ceiling; without this, delegation multiplies authority
instead of subdividing it.

A delegation chain SHOULD terminate in a human principal. An implementation
SHOULD report a chain that does not, because a tree of authority resolving to
nobody is the failure the whole model exists to prevent.

### 3.4 Enforcement modes

An implementation MUST support a ladder, weakest to strongest:

```
observe  →  shadow  →  canary  →  enforce
```

Under `observe`, decisions are evaluated and recorded and **nothing is refused**.
This is instrumentation, not governance, and an implementation MUST report it as
such wherever it lists a grant as a control.

A child grant MAY climb the ladder and **MUST NOT descend it**. A parent in
`enforce` delegating to a child in `observe` would produce a tree where every
bound is correctly narrowed on paper and nothing is enforced anywhere.

### 3.5 Revocation

Revoking a grant MUST revoke everything delegated from it. A revocation that
stopped one agent while its delegates kept running is a notice, not a control.

The question a revocation raises is not *was it revoked* but **was anything
allowed afterwards**. An implementation MUST be able to answer that, and MUST
treat actions allowed after the revocation timestamp as a breach rather than a
footnote.

## 4. Custody

Every signed artifact MUST state who held the signing key. A signature proves
*someone with the key produced this*; it cannot prove the signer did not produce
it later, over a rewritten history. Custody is what bounds that.

| Value | What a reader may conclude |
|---|---|
| `ephemeral` | Generated at startup, lost on restart. Development only. |
| `deployment` | The key is held by the party being governed, who could therefore re-sign a rewritten history. |
| `kms` | Non-exportable, held in a key management service. They can sign new records, not extract the key. |
| `hsm` | Non-exportable, held in an attached device. Requires no network. |
| `external` | Held by the customer or their auditor. The operator cannot sign without them. |

An implementation MUST NOT provide any means to export a private signing key,
and MUST NOT accept one through its API. The capability SHOULD be absent from
the interface rather than present and documented as forbidden.

An implementation claiming `external` MUST fail closed when that access is
withdrawn. Falling back to another key would produce records claiming a custody
they do not have.

## 5. The three-state discipline

Wherever this specification records a fact obtained from elsewhere, it MUST
distinguish three states, never two:

| Pattern | States |
|---|---|
| How a fact was obtained | `observed` · `asserted` · `not_recorded` |
| Whether a source stood behind it | `attested` · `unattested` · `absent` |

`not_recorded` MUST NOT be rendered as a negative finding, and MUST NOT be
rendered as a positive one. "We did not record this" is a third answer, and
collapsing it into either of the others manufactures a certainty nobody has.

This is the single most-violated rule in systems of this kind, and the one that
most reliably converts an evidence system into a liability.

## 6. Conformance

An implementation conforms to v0.1 if it:

1. Models agents with slug-plus-environment identity and a required accountable
   owner (§2.1).
2. Issues grants carrying at least the required fields (§2.2) and refuses to
   issue them to unowned agents.
3. Evaluates the nine gates in the specified order, debiting budget last (§3.1).
4. Records all six outcomes, including refusals (§2.4).
5. Enforces attenuation at issue time on all five axes, including enforcement
   mode (§3.3).
6. Cascades revocation through the delegation tree, and can answer what was
   allowed after it (§3.5).
7. States key custody on every signed artifact, recorded at signing time (§4).
8. Keeps the three-state discipline (§5).

Conformance tests are **not** part of v0.1. Publishing a conformance claim
without them would be asking implementers to grade themselves, which is the
practice this specification exists to replace.

## Out of scope for v0.1

Named because a specification is judged partly on what it declines to invent:

- **Contract language.** Conditions and policy are implemented; their grammar is
  not yet stable enough to specify without freezing decisions we expect to
  change.
- **Evidence schema.** The Merkle construction, canonical form and inclusion
  proof format are implemented and versioned, but a wire format others should
  interoperate with needs at least one other implementer's input.
- **OTel semantic conventions.** A mapping from the entity model to OTel spans
  is the obvious way to capture governed actions from an estate that already
  emits telemetry, and it should be proposed to OpenTelemetry rather than
  declared here. No implementation exists yet, in this project or elsewhere.
- **Conformance test suite.** See §6.
- **Identity federation between deployments.** No implementation, no proposal.
